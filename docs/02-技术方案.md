# 桃屁屁 · 技术方案（Mac / Windows 通用）

> 本文回答两个关键问题：
> 1. 跨平台怎么选（统一 vs 原生）？
> 2. 桌面宠物（透明置顶 + 帧动画 + 托盘 + 番茄 + 看板 + Steam）具体怎么搭？

---

## 1. 结论先行（TL;DR）

- **推荐：单一代码库跨平台（Tauri 2.x 或 Electron），不要首版就拆双原生。**
- 桌面宠物是「轻 UI + 大量 2D 帧动画 + 常驻后台」的场景，**Web 渲染层 + 轻量壳** 是最划算的路子。
- 若你愿意「每个平台原生重做」，那是对极致流畅度/内存的投入，但**首版不建议**，会双倍拖慢 MVP。

### 选型建议（给结论）

| 优先级 | 方案 | 什么时候选 |
|---|---|---|
| ⭐ 推荐 | **Tauri 2.x（Rust 壳 + Web 前端）** | 想要体积小、内存低、专业感强、愿意碰一点 Rust |
| ⭐ 备选 | **Electron（Node 壳 + Web 前端）** | 想要最快出活、生态最熟、Steam 集成资料最多 |
| 进阶 | **双原生（Swift/AppKit + C#/WPF 或 WinUI 3）** | 首版验证后，追求极致体验/最低内存再重构 |

> 我的个人倾向：**首版用 Electron 打 MVP（最快验证），跑通后再评估是否换 Tauri 减体积**。二者共享同一套「Web 渲染层」，迁移成本比你想的小。下文按「统一方案」展开，并给出原生方案的等价映射。

## 2. 总体架构（三层）

```
┌────────────────────────────────────────────────────────────┐
│ ① 资产层（素材）                                            │
│   透明精灵图/精灵表(APNG/WebP/PNG 序列) + 音效 + 文案表      │
├────────────────────────────────────────────────────────────┤
│ ② 应用层（逻辑，TypeScript 跨平台共享）                      │
│   提醒调度器 │ 番茄状态机 │ 游戏化引擎 │ 统计服务 │ 设置      │
├────────────────────────────────────────────────────────────┤
│ ③ 壳层（平台适配，唯一有平台差异的地方）                     │
│   Electron/Tauri：透明置顶窗口 │ 托盘/菜单栏 │ 系统通知 │ 开机自启 │ 自动更新 │ Steamworks │ 本地存储 │
└────────────────────────────────────────────────────────────┘
```

**核心原则**：90% 逻辑写在 ②（纯 TS），平台差异全部收敛到 ③ 的适配接口里，方便将来换壳（Electron ↔ Tauri ↔ 原生）。

## 3. 关键决策 1：跨平台方案对比

| 维度 | Electron | Tauri 2.x | 原生（Swift + WinUI） |
|---|---|---|---|
| 单代码库 | ✅ | ✅ | ❌ 双套 |
| 透明窗口/置顶 | ✅ 成熟 | ✅ 可用 | ✅ 最可控 |
| 点击穿透 | ✅ setIgnoreMouseEvents | ✅ | ✅ |
| 托盘/菜单栏 | ✅ Tray | ✅ | ✅ |
| 系统通知 | ✅ | ✅ | ✅ |
| 包体 | 大(~100MB+) | 小(~10MB) | 最小 |
| 常驻内存 | 80~150MB | 40~90MB | 30~60MB |
| Steam 集成 | steamworks.js / greenworks | Rust steamworks crate | 原生 SDK |
| 前端生态(动画/图表) | 全部可用 | 全部可用 | 需自绘 |
| 上手成本 | 低 | 中（Rust 打包/权限） | 高（两平台各来一遍）|
| 生态/踩坑资料 | 极多 | 多 | 平台官方 |

**为什么首版倾向 Electron**：
1. 透明置顶 + 鼠标穿透 + 多显示器 + 托盘，这些「桌面宠物」的命门在 Electron 里成熟且坑最少。
2. Steam 上架用 `steamworks.js`，成就/统计/云存档都有现成绑定。
3. 数据看板、动画、图表全用 Web 技术，和宠物窗口共享渲染，开发最快。

**为什么将来可能换 Tauri**：体积和内存对「常驻小工具」的差评影响很大，等 MVP 验证完需求，把 ② 的 TS 逻辑和 Web 前端原样搬进 Tauri 即可，成本主要是打包与权限适配。

## 4. 关键决策 2：桌宠动画用什么格式（回答「是不是 GIF」）

**结论：每个交互动作 = 一段「透明背景循环动画」，但不要用 GIF，用「精灵表 PNG 序列」或 APNG/WebP。**

| 格式 | 透明 | 半透明 | 颜色 | 体积 | 引擎支持 | 结论 |
|---|---|---|---|---|---|---|
| GIF | ✅ 1bit | ❌ 无 | 256 色(易banding) | 大 | 通用 | ❌ 仅兜底 |
| **APNG** | ✅ | ✅ | 真彩 | 中 | 好 | ✅ 推荐(单文件) |
| **WebP(动图)** | ✅ | ✅ | 真彩 | 小 | 好 | ✅ 推荐(体积最小) |
| **PNG 精灵表/序列帧** | ✅ | ✅ | 真彩 | 中(可控) | 最好 | ⭐ 最推荐(引擎可控) |
| 透明 WebM(VP9 alpha) | ✅ | ✅ | 真彩 | 小 | 需解码 | 备选 |

### 推荐方案：**精灵表（sprite sheet）+ 帧动画引擎**
- 把一段动作的每一帧（已抠好透明背景）拼成一张大图或按序号命名的一组 PNG，运行时由渲染引擎按帧播放。
- 优点：帧率/循环/混合/暂停/正倒放全部可编程；半透明、发丝级边缘、粒子都能保留；方便做「程序化呼吸」叠加。
- 渲染引擎：**PixiJS**（WebGL，帧动画 + 粒子 + 混合模式最强）或原生 Canvas。

### 为什么可以「不用建模、纯视频」？
- 桌面宠物是 **2D 帧动画**，本质是「一帧帧透明图按顺序播放」。视频只是一堆帧的容器，抽帧 + 抠图后就和手绘序列帧完全等价。
- 没有 3D 模型完全没问题，业界大量桌宠（Shimeji 系、各种桌面宠物）都是帧动画。
- **注意事项**：视频帧率一般 24~30fps，动作短（1~3s），抽帧后单动作 24~90 帧；建议降到 15~20fps 减少体积，逐帧边缘要干净。

## 5. 素材管线（视频 → 透明动画）总览

> 详见《03-素材处理方案.md》。此处给技术侧结论：

```
即梦视频(MP4，绿幕/纯色背景)
   → ffmpeg 抽帧(15~20fps) → PNG 序列
   → 背景抠除(绿幕 chroma key 或 AI 分割 rembg) → RGBA PNG 序列
   → 打包(精灵表 / APNG / WebP) + 尺寸规范化(如 512×512)
   → 资产清单 manifest.json（动作名/帧数/帧率/循环/锚点）
```

- **绿幕路线**：让即梦生成时用**纯绿/品红背景**，抽帧后 `chromakey` 一键去背，边缘最干净、最快。
- **AI 路线**：任意背景视频用 `rembg`（U²-Net）逐帧抠图，边缘可能有闪烁，需后处理（去噪/羽化）。
- **两者可叠加**：绿幕为主，AI 做边缘修复。

## 7. 桌面宠物窗口的关键实现要点

### 7.1 透明置顶窗口（Electron）
- `BrowserWindow`：`transparent: true`、`frame: false`、`alwaysOnTop: true`、`skipTaskbar: true`（宠物本体不进任务栏，只有托盘入口）、`resizable: false`、`hasShadow: false`。
- macOS：`window.setVisibleOnAllWorkspaces(true)`（跨桌面空间可见）+ `setAlwaysOnTop(true, 'screen-saver')` 层级。
- Windows：`alwaysOnTop` 需处理与全屏应用的层级冲突。

### 7.2 鼠标穿透
- 宠物身体外区域 `setIgnoreMouseEvents(true, { forward: true })`，让鼠标能点穿到宠物背后的应用；悬停在宠物身上时切换回可交互。
- 这是「不挡操作」的关键，Electron 用 `setIgnoreMouseEvents`，配合 `mousemove` 命中检测。

### 7.3 贴边 / 拖动 / 多显示器
- 拖拽用 `-webkit-app-region: drag` 或手动 `screen.getCursorScreenPoint()` 移动窗口。
- 记住窗口位置（每块显示器），重启恢复。

### 7.4 性能
- 宠物窗口单独一个轻量 renderer；看板放独立窗口，需要时才创建。
- 待机降到 15~20fps，失焦/全屏降到 5fps（`requestAnimationFrame` 节流）。
- 动画只重绘宠物画布，不跑整页 DOM。

## 8. 番茄计时 + 托盘/菜单栏

### 8.1 番茄状态机
```
IDLE → WORK(默认25min) → BREAK(默认5min) → IDLE
            └──(专注中抑制非必要提醒)
```

### 8.2 菜单栏（macOS）/托盘（Windows）倒计时
- Electron `Tray` 用 `setTitle("25:00")`（macOS 状态栏可直接显示文字；Windows 托盘文字支持有限，用 tooltip + 气泡或图标角标）。
- 倒计时每秒更新标题；结束发系统通知 + 宠物欢呼动画。
- 菜单项：开始/暂停/跳过/重置、切模式、打开看板、设置、退出。

### 8.3 关键点
- 计时器放主进程（壳层）而非渲染进程，避免宠物窗口失焦被节流导致计时不准。
- 用时间戳差值计算，避免 `setInterval` 漂移。

## 9. 提醒调度器

- 单例调度器（主进程），基于「间隔 + 窗口时段 + 勿扰态」计算下一次提醒时间。
- 每类提醒独立状态：`pending → 触发(前摇动画) → 弹气泡 → 已响应/延后/忽略`。
- **与压力系统联动**：提醒被「延后/忽略」→ 压力值 +10（呼应核心机制，见 §10）。
- 与番茄状态联动：专注中，非番茄提醒延后；专注结束统一补发。
- 久坐提醒需结合「当前是否在活跃输入」判断（可选，需监听全局键鼠，注意权限与隐私）。

## 10. 压力·血量状态机 + 数据模型（SQLite）

### 10.1 压力·肿胀状态机（核心，跑在主进程）

```
压力值 P (0–100)：
  上升：工作/专注中随时间匀速 (+1/min，可配)；番茄专注 ×1.3；忽视提醒 +10
  下降(泄压)：点击/抚摸 -5(冷却 30s)；喝水/起身/上厕所打卡 -20；番茄休息 -15

肿胀阶段（驱动动画）：
  P 0–25    normal     待机呼吸
  P 25–50   puff       微鼓
  P 50–75   swell      鼓胀
  P 75–99   critical   濒临爆炸(颤抖/预警闪烁)
  P 100     explode    → 播爆炸动画 → 血量 -25 → P 归零 → 进入 deflate(瘪掉)
  deflate → reinflate：连续点击 / 完成任意健康打卡 → 恢复 normal
```

- 压力值建议**只在工作/专注态增长**，合盖/长时间空闲不增长（避免「挂机爆炸」误伤）。

### 10.2 SQLite 数据模型

```sql
-- 事件表：所有可统计行为（含压力/血量变化）
events(id, type, ts, meta)
-- type ∈ water | stand | toilet | pomodoro_start | pomodoro_done
--      | click_relief | pet_relief | ignore_remind
--      | pressure_tick | explode | deflate | reinflate | level_up | ...
-- meta: 压力变化量 / 血量变化量 / 番茄时长等

-- 每日聚合（看板用，可惰性生成）
daily_stats(date,
  water_count, stand_count, toilet_count,
  focus_minutes, pomodoro_count,
  explode_count,            -- 当日爆炸次数
  hp_end, hp_min, hp_avg,   -- 当日血量(结束/最低/平均)
  pressure_peak,            -- 当日压力峰值
  relief_count, ignore_count, streak)

-- 设置
settings(key, value)   -- 提醒间隔/文案/皮肤/音量/压力系数/爆炸扣血等

-- 成就
achievements(id, unlocked_at)

-- 成长/等级（血量驱动）
profile(xp, level, growth, hp, current_streak, best_streak)
-- growth: 长期成长值，每日按血量结算增减；hp: 当前血量
```

- 隐私：本地文件，不包含屏幕内容；Steam 云存档只同步 `profile/achievements/settings`（可选）。

## 11. Steam 上架集成

| 特性 | 实现 |
|---|---|
| `steam_appid.txt` / 应用 | Steamworks 后台创建 app |
| 成就 | 映射到「连击/升级/打卡」事件 |
| 统计(Stats) | 喝水次数、专注分钟等同步到 Steam |
| 云存档 | 同步 profile/settings |
| Overlay | 默认可用；宠物需注意置顶层级与 Overlay 冲突，可降级处理 |
| 上架流程 | Steamworks 账号 → 交 $100 → 建 App → 集成 → 上传构建(depot) → 商店页(截图/描述/定价) → 审核 |

> 注意：Steam 要求游戏「非挂机工具」形象，商店页重点突出**养成 + 健康陪伴**的玩法，弱化「纯提醒工具」。

## 12. 打包与分发

- Electron：`electron-builder` 出 `dmg`(mac) + `nsis`/`portable`(win)。
- macOS：需签名 + 公证（notarization），否则被 Gatekeeper 拦；Steam 分发可借 Steam 的公证。
- Windows：代码签名证书（可选，影响 SmartScreen 提示）。
- 图标/菜单栏图标：多分辨率 + macOS 模板图标（黑/白）。
- 自动更新：Electron `electron-updater`（Steam 平台可交给 Steam 自动更新，两者二选一避免冲突）。

## 15. 风险与对策

| 风险 | 对策 |
|---|---|
| 透明窗口两平台行为不一 | 抽象「窗口适配层」，MVP 阶段双平台各测一遍 |
| 常驻内存高（Electron） | 拆进程、降帧、MVP 后评估迁 Tauri |
| 托盘倒计时平台差异 | macOS 用标题文字，Windows 用 tooltip+气泡 |
| 帧动画体积大 | 降帧率、精灵表压缩、按需加载 |
| 即梦素材角色漂移 | gpt-image-2 图生图锁角色 + 统一提示词模板 |
| Steam 与自动更新冲突 | 上架后以 Steam 更新为主 |
