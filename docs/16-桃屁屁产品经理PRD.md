## 3. 现有交互盘点（按用户视角）

### 3.1 桌宠交互
- **悬停**：头顶显示短气泡（"我会安静陪你" / 倒计时 / 休息倒计时 / "点我开始休息"）
- **悬停 2 秒**：摸头反馈（`pet.webm` + "好舒服呀…再摸摸"）
- **左键单击**：状态相关反馈；连续点击 3 次以上变害羞（`shy.webm` + "别、别一直戳啦…"）
- **冷落 10 分钟**：插播 `bored.webm` 求关注
- **右键菜单**：专注（25/45/60/开始/暂停/继续/取消）+ 4 项打卡 + 打招呼 + 小屋
- **拖动**：位移 >5px 视为拖动，单击不触发

### 3.2 番茄钟
- 25/45/60 分钟可设，默认 25
- 短休 5 分钟，长休 15 分钟（每 4 个番茄）
- 番茄结束进"等待用户点击休息"状态——不自动进入休息，给用户主动权

### 3.3 4 项打卡（每轮休息 + 独立提醒）
| 项目 | 角色动作 | 单次时长 |
|---|---|---:|
| 活动一下 | `activity.webm` | 4s |
| 喝水 | `water-prompt` (`dry.webm` 1.45–9.8s) | 8.35s |
| 上厕所 | `toilet.webm` | 5.8s |
| 护眼 | `eye-strain.webm` | 5s |

### 3.4 独立提醒（番茄外的并行机制）
| 提醒 | 默认间隔 |
|---|---:|
| 喝水 | 45 min |
| 活动一下 | 50 min |
| 上厕所 | 120 min |
| 护眼 | 20 min |

- 专注期间到点延后
- 一次只展示一个
- 喝水忽略 15 min → 切到 `dry` 干裂状态
- 护眼忽略 10 min → 红眼干裂夸张态

### 3.5 反久坐 + 爆炸
- **连续专注上限默认 40 分钟** → 爆炸
- 压力增速 = 100 ÷ 上限分钟数（默认 2.5 点/min，保证变红过程完整可见）
- 压力 ≥55 → `pressure` 视觉（`pressure.webm` 按压力值取帧，越高越红）
- 爆炸：扣分（15/30/50 累进）+ 全屏"快去休息啦"（5.2s）+ 进入瘪气
- 瘪气：必须真实离开电脑 5 分钟才恢复（监听系统空闲 + 计时）

### 3.6 陪伴感 / 成长
- 每日首次启动：打招呼 + 时段文案 + 昵称
- 里程碑 7/30/100 天：`dance.webm` + 撒花 + "我们互相陪伴 N 天啦"
- 成长等级（桃苗 → 小桃 → 圆桃 → 蜜桃 → 仙桃）：`transform.webm` + 撒花 + "我长大啦"
- 深夜 23:00–6:00：自动 sleep 模式，抑制无聊和小动作
- 撒娇/害羞/摸头：陪伴感微交互

### 3.7 统计
- 桃桃小屋 Dashboard：今日能量 / 番茄数 / 7 天趋势 / 行为次数 / 7 枚徽章
- 健康分：喝水 8/活动 12/如厕 6/护眼 5/休息 10（每项有每日次数上限）
- 爆炸扣分 15/30/50 累进；和好奖励（恢复当天首次打卡 +5）

## 4. 产品评估：是否达到个人管理目的

### 4.1 达到的部分 ✅
- **番茄钟 + 4 项打卡** 完整，能让用户在工作节奏里有结构化的休息
- **独立提醒** 提供番茄外的健康节律
- **爆炸机制** 提供强负反馈，让人不敢连续干太久
- **数据可视化**（小屋 Dashboard）让用户看到自己的趋势
- **陪伴感**（撒娇/害羞/深夜/摸头/里程碑）让用户真的舍不得关掉应用

### 4.2 没达到的部分（本次大改核心）❌
| 问题 | 用户反馈原文 | 现状 | 影响 |
|---|---|---|---|
| 提醒不够"重" | "现在所有的到点提醒，我想在屏幕上铺开" | 只是个 3.2 秒气泡 | 用户专注时根本看不见，气泡太小、太短 |
| 喝水反馈太轻 | "喝水应该干裂→碎掉→补水拼回" | 当前只有"忽略 15 分钟才切 dry" | 没有渐进感，用户感知不到"自己在变干" |
| 反久坐缺过程 | "不是触发了之后再爆掉，而是随着时间越来越大" | 当前是 0→100 压力值，55→pressure 视觉，100→爆炸 | 体验像"等到点突然炸"，缺乏"逐渐变胖"的过程感 |
| 护眼只播一次 | "点击护眼，他就和你一起揉眼睛，1-2min，一直做眼保健操" | 当前是 5s 一次性播放 | 用户点完只能看 5 秒，无法跟做 |
| 活动提醒太短 | "跳一跳，稍微起来走两圈，也可以有一个小动画" | 当前是 4s 一次性 | 还没起身就播完了 |
| 喝水打卡 | "只需要喝水打卡吧，其他的就是她提醒你，你看见她这样了也跟着做" | 当前 4 项都能直接打卡 | 用户其实想被提醒后自己真的做了再回来点一下 |

## 5. 本次大改：交互重定义（To-Be）

### 5.1 大屏接管（P0，**核心**）

到点提醒不再只是气泡，而是触发**大屏接管层**：桃屁屁铺满屏幕中央 + 大字指向提示 + "我去了我去了…" 确认按钮。

**触发条件**：
- 反久坐到阈值（见 5.2）
- 喝水提醒到点
- 活动提醒到点
- 护眼提醒到点
- 上厕所提醒到点

**视觉规范**：
```
┌─────────────────────────────────────────────┐
│                                             │
│           [桃屁屁动态视频 / 撑爆 / 干裂]      │
│                                             │
│      该喝水啦！                              │
│      我都干成这样了 😢                        │
│                                             │
│           [ 我去了我去了… ]                  │
│                                             │
└─────────────────────────────────────────────┘
```

**交互细节**：
- 大字标题 + 副文案（桃屁屁第一人称抱怨）
- 桃屁屁不停做对应动作（干裂、跳、揉眼、膨胀），不能停
- 唯一出口："我去了我去了…" 按钮
- 点击后：屏幕收回 + 桃屁屁回小窗 + 播放 happy 反馈动画 + 记录行为
- **不抢焦点**（用 BrowserWindow 的 `alwaysOnTop` 但不 `focusable`），用户可继续做事但一定会看见

**实现要点**：
- 复用现有 `.alert-view` 全屏容器，但加 `<button>` 和"动起来"循环
- 反久坐态需要桃屁屁视频**持续 grow**（见 5.2），这是技术难点
- 其余 4 项的桃屁屁动作已有素材，loop 即可

### 5.2 反久坐：渐进膨胀（P0，**最难**）

**目标**：用户到点不休息，桃屁屁**不是先憋到 100 然后突然炸**，而是**随着时间持续变大变红**，到阈值才爆。

**核心机制**：
- 新增 `swellLevel: 0..3` 状态字段，秒级推进
- 触发条件：连续专注满 X 分钟（X = 上限的一半，默认 20 分钟）
- 进度公式：`swellLevel = min(3, floor((专注分钟数 - X) / step))`，step 默认 5 分钟
  - swellLevel 0（轻微胖）：粉色 + 小红脸 + 轻微喘气
  - swellLevel 1（明显胖）：更红 + 肚子鼓起来 + 喘
  - swellLevel 2（危险）：通红 + 接近圆形 + 摇晃
  - swellLevel 3（即将爆）：几乎贴满屏幕 + 表情狰狞 + 大字"撑不住了"
- swellLevel 0–2：桌宠小窗内 grow（**不是视频**，是 CSS transform: scale + 视频 seek 到对应阶段）
- swellLevel 3：触发大屏接管（见 5.1），视频播 `explosion.webm` 全屏
- 爆炸后：瘪气，**必须**真实离开电脑 5 分钟才能恢复

**素材**：
- `swell-1.png`（已有 assets/generated/final）轻度胖
- `swell-2.png`（已有）中度胖
- `swell-3.png`（已有）极度胖
- `pressure.webm`（已有）按压力取帧 → swellLevel 3 的通红状态直接用这段

**实现**：不用新视频。`PetMotion` 接收 `swellLevel` 参数，按级别切换 still PNG + CSS scale(1.0/1.15/1.3/1.5)。

**鼠标键盘活动监听**：原"恢复"逻辑已有（系统空闲 5 分钟）。swell 期间不监听活动——**只要到点了就 swell，活动不会让它回退**，只会延缓到达 swellLevel 3 的速度（活动时 swellLevel 推进按"实际流逝时间"，而非"挂机时间"）。这符合用户描述："不是触发了之后再爆掉，你看看这个怎么做到，如果是视频的话"——答案是**不用视频，用多档静态图 + transform scale**。

### 5.3 喝水：干裂→碎掉→修补（P1）

**阶段**：
| 阶段 | 触发 | 视觉 | 气泡 |
|---|---|---|---|
| 正常 | 到点前 | 默认 dry 不播 | "记得喝水哦" |
| 轻微干裂 | 到点 | `dry.webm` 0.08–1.45s 末帧 | "我有点干啦…" |
| 严重干裂 | 提醒忽略 15 min | `dry.webm` 持续循环 + 红脸 + 裂纹 | "快喝水！我要碎啦！" |
| 碎掉 | 忽略 30 min | 视频分镜碎裂（仍可用现有 dry 末帧 + CSS shake） | "我碎了……不理我了吗" |
| 喝水修补 1 | 用户喝水 1 次 | `dry.webm` 1.45–5s（恢复段）+ 轻微抖动 | "谢谢你…我再喝点…" |
| 修补 2 | 用户喝水 2 次 | `dry.webm` 5–7s + 抖动减少 | "好多了好多了！" |
| 完全恢复 | 用户喝水 3 次（或达到时间阈值） | 回 idle | "满血复活啦！下次记得早点喝水哦" |

**实现**：`dryStage: 0..3` 字段 + `hydrateCount` 计数，喝水打卡每次 `+1`，满 3 次回正常；或每个 stage 有最低恢复时长。

### 5.4 护眼：1-2 分钟跟做模式（P1）

**现状**：eye-strain.webm 5s 一次播放 → 用户没法跟做
**改进**：
- 点击"护眼" → 大屏接管（见 5.1）→ 桃屁屁循环播放 eye-strain.webm（**完整 1-2 分钟**）→ 显示倒计时"还剩 1:42"
- 倒计时结束自动收回
- 期间可点"我去了"提前结束

**素材**：复用现有 eye-strain.webm，loop 即可，无需新视频

### 5.5 活动：跳一跳 + 走两圈（P1）

**现状**：activity.webm 4s 一次播放
**改进**：
- 点击"活动一下" → 大屏接管 → 桃屁屁循环播放 activity.webm → 气泡"跟着我跳！" + 倒计时 60s
- 60s 后自动收回
- 期间可点"我去了"提前结束

**素材**：复用现有 activity.webm，loop 即可

### 5.6 喝水唯一打卡项（P2 决策）

**用户原话**："整个只需要喝水打卡吧，其他的就是她提醒你，你看见她这样了，你也就可以跟着做"

**当前实现**：4 项都能右键直接打卡（`rest:complete` 等 action 路径）

**建议改动**：
- 右键菜单"记录健康行为"组**只保留"喝水"**
- 其他三项只在**番茄休息**或**大屏接管后**的"我去了"按钮触发时记一次
- 这样行为数据更真实——避免用户随手打卡糊弄

## 6. API 决策：MCP vs 直连

### 6.1 现状
- 当前使用 **MiniMax-H3 API 直连**（不是 MCP）
- 体现在 `docs/06-MiniMax视频生成清单与提示词.md`、`scripts/build-generated-sprite-motion.py` 等工具中
- 20 条视频素材中 6 条陪伴感素材（eye-strain/activity/pet/bored/shy/dance/deflated）由 H3 图生视频生成

### 6.2 MCP 与 API 直连对比

| 维度 | MCP（自部署 stdio/SSE） | API 直连（当前） |
|---|---|---|
| 部署形态 | 本地 Python/Node 进程，需安装 `minimax-mcp` | 直接 `curl` 调 `api.minimaxi.com` |
| 鉴权 | 同一 MiniMax API Key | 同一 MiniMax API Key |
| 视频能力 | `generate_video` / `image_to_video` / `query_video_generation` 三个工具 | 同样三个接口，无差异 |
| 语音/音乐/文生图 | 支持（更广） | 需自己接对应 endpoint |
| 网络出网 | 本地进程调 API，**不绕开网络** | 直接发 HTTPS |
| 调用延迟 | 多了本地进程 IPC 跳 | 直连，更低 |
| 维护成本 | 多一层进程 + 协议 | 单一 HTTP 调用 |
| 当前项目需求 | 只需要视频生成 | 视频生成就够 |

### 6.3 决策结论
**保持 API 直连，不接 MCP**。原因：
1. 当前 MCP 没有提供 API 直连之外的视频能力
2. 多了本地进程层只增加维护成本
3. 自部署 MCP 不绕开 API 配额/计费/速率限制
4. 官方文档本身就建议用 CLI/SDK 替代 MCP
5. 真正需要 MCP 的场景是：同时混用多种模型能力（语音 + 音乐 + 视频）且不想自己封装。当前项目无此需求

**后续若需扩展**：等真的需要 TTS 或音乐生成时再评估 MCP 价值，**目前保持简单**。

### 9.1 风险
